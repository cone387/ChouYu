## Mem0 主引擎修复门禁

本机配置了自托管 Mem0。代码检查发现：

- `Mem0MemoryProvider.update` 调用追加式 `push`，已有 `chouyu_id` 的记录被跳过，因此编辑不会更新远端。
- `delete` 继承 SQLite 行为，没有对应的远端删除。
- 远端上传通过后台 Promise 执行，失败只记日志，调用方无法用成功返回值证明远端已保存。

在修复修改确认、远端标识映射、失败处理并完成隔离测试用户的实际读写/清理前，不能宣称 Mem0 主引擎的增删改查验收通过。`rc.2` 候选包仍包含这些限制，应继续保持未正式发布状态。

工作区已接入 `updateConfirmed` / `deleteConfirmed`：先确认 ID 在配置用户范围内，再执行远端操作；编辑还会读回正文，确认后才修改本地。SQLite 持久化远端 ID 映射，重启后仍能删除同一条远端记录。13 项适配器测试覆盖请求字段、用户范围、路径编码、拒绝、204，以及服务器返回成功却未修改内容的情况。

真实服务暴露了一个单测未发现的问题：OSS HTTP PUT 使用 `text`，而 Python SDK 使用 `data`；发送 `data` 时服务可以返回成功但不修改正文。已修正 HTTP 字段并增加读回验证。失败报告保留在 `evaluations/mem0-live-2026-09-07*.json`，前两次测试的残留分别通过 `mem0-cleanup-first.json`、`mem0-cleanup-second.json` 确认清理。

[最终实际验收报告](evaluations/mem0-live-2026-09-07-approval.json)覆盖创建、读取、候选确认写入、搜索缓存、编辑和重启后删除，全部通过且 `cleanupPassed=true`。每次使用随机隔离用户，只写合成内容，没有修改原用户记忆。

手动确认和普通自动新增路径已等待远端写入并读回；失败时保留 pending 候选、向调用方报错，可重试。Electron 运行时覆盖认证失败保留候选、恢复后重试、编辑/删除失败保留缓存与重启后删除。批量导入、冲突替换、历史恢复、清空和跨用户缓存隔离仍需统一处理，不能把这些单条操作的验收解释为整个主引擎已完成。后续修正尚未进入 `rc.2` 安装包。

参考：[Mem0 REST API](https://docs.mem0.ai/open-source/features/rest-api) 提供按 memory ID 的 PUT/DELETE，主引擎需要显式使用这些操作；追加式同步去重不能代替主引擎更新。

## 跨用户与历史恢复补充验收

Mem0 缓存现在按引擎类型、规范化服务地址和用户 ID 的 SHA-256 分别存储为 `chouyu-memory.db.mem0-<hash>.db`，不再与本地 SQLite 主引擎共用数据库。密钥轮换不改变缓存归属。切换配置后，下次访问自动加载对应数据库；旧连接的异步结果在写缓存前检查归属。

原 `chouyu-memory.db` 保持原样，旧版混合缓存不会自动搬到任何远端用户，避免把归属不明的记录当成该用户的记忆。旧库中的未上传候选仍保留，可在本地引擎中检查；远端已保存的记录可以重新检索到新缓存。本次不删除任何旧库。

Electron 运行时通过：A→B 用户切换、旧搜索结果晚到被拒绝、B 无法删除 A 的本地 ID、切换本地引擎无远端缓存混入、切回 A 后候选仍存在。证据为 `CHOUYU_MEM0_SCOPE_SMOKE_PASSED`；这是实际 Electron/SQLite 配合本地协议服务的隔离验证。

历史恢复使用远端 PUT 并读回后才提交本地修订；认证失败保留当前版本。真实服务报告 [mem0-live-2026-09-07-history.json](evaluations/mem0-live-2026-09-07-history.json) 全部通过，包括候选确认、搜索、更新、恢复历史、重启后删除，且清理成功。

无冲突批量导入现在等待远端确认，失败计数准确，重复导入会重试 pending 候选；导入途中切换连接不会将剩余数据写入新用户。失败后重试通过运行时测试。冲突替换/并存、归档恢复、清空以及其他同步接口仍需继续审计，因此完整主引擎门禁保持未完成。

## 归档和冲突补充验收

归档把 `chouyu_status=archived` 保存到远端，保留远端正文和本地历史，聊天召回过滤归档记录；重新启用等待远端属性读回后再改变本地状态。批量归档逐条提交，部分失败会报告本次已完成的数量，不能视为跨网络事务。

冲突替换逐条归档旧记录并保留修订，再确认新候选写入；并存保留旧记录，拒绝仅处理未写入的候选。发生中途失败时保留 pending 候选和未解决冲突，已确认归档的旧记录不会伪装成仍启用；可重试或重新启用旧记录。自动身份替换和导入冲突也等待异步确认。搜索与这些操作串行，防止旧搜索结果覆盖刚完成的归档状态。

真实报告 [mem0-live-2026-09-07-conflict.json](evaluations/mem0-live-2026-09-07-conflict.json) 包括归档后不召回、重新启用、冲突替换、恢复旧记录和重启后删除，全部通过，测试数据已清理。Electron 另用“PUT 成功、创建返回 503”的故障注入验证部分替换、候选保留和重试。清空及遗留同步入口仍待补齐。

适配器读回现在同时检查正文和提交的属性，避免服务忽略归档状态却被判成功。单测增加对应拒绝用例，总计 254 项。既有子进程测试曾因 500ms 冷启动期限超时：正常连接改用 3 秒，专门超时用例仍为 500ms，并分别校验超时/退出/协议/大小错误，避免不同故障相互冒充通过。

## 清空与统一确认入口

`clearConfirmed` 从当前远端用户列表读取并逐条删除，包括尚未缓存到本地的记录；每次 DELETE 后读回确认 ID 消失，再移除对应缓存。远端列表为空才清除剩余本地候选。失败会报告已删除数量并保留其余状态；单次最多处理 10000 条，达到上限会明确报未完成。期间切换配置会中止对新用户的操作。

已经移除 Mem0 的后台追加写入。主服务和 IPC 使用异步确认方法，旧同步写入入口会在修改前明确抛错；原始消息提取、搜索和确认写入在同一队列中执行。删除/拒绝 pending 候选也会检查其 ID 是否曾在远端写入，避免请求结果未知后留下远端副本；不会仅凭 pending 候选正文删除另一条同文记录。

真实报告 [mem0-live-2026-09-07-clear.json](evaluations/mem0-live-2026-09-07-clear.json) 的全部操作通过，包括最终清空，清理成功。Electron 覆盖清空认证失败保留数据、删除未缓存记录和本地候选、其他用户不受影响、旧同步入口无副作用。255 项单测通过，包含“服务返回 204 但记录仍存在”的拒绝用例。

界面通用操作失败后刷新已提交状态再展示原错误；清空确认框内展示错误并禁止重复提交。当前 Mem0 设置仍采用“概览/连接”布局，上述远端管理能力主要由主服务/IPC 与验收入口验证，不能据此声称远端记忆库的完整管理 UI 已开放或已验收。
