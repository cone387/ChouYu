# Agent 通用能力核对（2026-10-27）

核对基础：已合并的架构加固 `76fc11d`；当前能力方向见 [用户纠正后的说明](superpowers/specs/2026-10-27-agent-autonomy-direction.md)。以下首轮观测记录保留修复前事实；用户确认继续后，已实现本文末尾的首批增强。没有新增模式，也没有调用真实在线模型。

## 结论

现有 agent 已能规划一轮工作、读取授权资料、保存成果、连续调度，并在必要追问或拟议结束时做边界复核。当前最值得补强的是跨轮信息的主动读取，以及规划与执行使用的信息一致性。

不能把这些缺口概括为“没有记忆”或“读不到任何旧成果”：数据实际存在，显式修订路径也能读取较早正文。具体问题在于数据如何进入下一次决策，以及后台 agent 是否有通用、只读的回看入口。

## 核对方法

使用真实 `WorkLoopHost`、SQLite、Native/DSH background harness 和本地 HTTP 模型夹具。创建同一任务的五份成果，将唯一标记分别放在首份正文、用户明确的任务范围记忆、已保存的成果认可意见和模型研究记忆中。关闭并重新打开 host 后，先核对这些记录仍存在，再捕获下一轮实际发给 provider 的规划/写作输入及工具目录。

普通轮次之后增加正向对照：规划明确选择首个成果分节进行修订，检查写作输入能否取得其原始正文。夹具只选择已支持的动作，不模拟模型自主能力优劣。

| 实际观测 | Native | DSH |
| --- | --- | --- |
| 重开后旧正文、用户记忆、反馈、研究记忆仍存在 | 是 | 是 |
| 规划输入包含开轮已选中的任务记忆标记 | 否 | 否 |
| 写作输入包含该任务记忆标记 | 是 | 是 |
| 普通轮次规划/写作输入包含较早正文标记 | 否 | 否 |
| 普通轮次规划/写作输入包含历史认可意见标记 | 否 | 否 |

测试开启后台技能工具能力但未装入额外自定义技能，实际写作工具目录为 `list_contact_materials`、`read_contact_material`；规划工具目录为空。不能把此结果扩大为对所有自定义技能或普通聊天工具的断言。

## 具体缺口

### 1. 规划与执行的信息不一致

[`scheduling.ts`](../src/main/task-center/contact/scheduling.ts) 在开轮时选择任务相关记忆，附上近期报告和有限正文；[`workflow.ts`](../src/main/workloop/workflow.ts) 的 `choose` 请求提供目标、进展、当前反馈和成果目录，却未包含已选择的记忆或近期报告正文。写作请求随后才拿到这些内容。

隔离场景证实：同一轮、同一条有效任务记忆，规划看不到而写作能看到。因此先前偏好、经验或条件可能在选取动作时缺席。它们是否实际造成一次错误选择仍取决于模型和任务；本轮证明的是信息传递差异。

### 2. 缺少后台通用的只读回看通路

[`delivery.ts`](../src/main/agents/delivery.ts) 保存累计目录，但默认只提供最近三个分节；开轮只附最近三份报告。这是上下文控制，不应简单改为每次塞入全部历史。

当前 `sectionId` 通路用于读取并修订旧分节，不是“先查几份历史再决定下一步”的通用检索接口。[`model.ts`](../src/main/workloop/model.ts) 内建后台工具主要组合技能与上传资料工具；[`memory-tools.ts`](../src/main/agents/memory-tools.ts) 中已有的聊天记忆读取工具并未作为后台通用读取能力接入。

历史反馈在 [`feedback-ledger.ts`](../src/main/agents/feedback-ledger.ts) 中持久存在，修订请求也会带入对应反馈；这不等于普通后续轮次能够检索任意较早意见。此次认可意见标记未进入普通轮次。认可意见也不能无条件升级为永久指令，读取时仍需保留意见类型、对象、版本和适用范围。

建议下一批优先复用现有查询服务，补齐本联系人/当前任务范围的记忆、成果和反馈检索/读取；让模型按需取正文，记录实际读到的来源与版本。不能为了开放检索而恢复此前已修复的接单/规划工具越界问题。

### 3. 工作假设与已确认记忆之间缺少可回看的衔接

[`memories.ts`](../src/main/agents/memories.ts) 将模型研究记忆保存为 `candidate`，默认选取只包含 `active`；夹具中的早期研究结论确实保存为候选，但后续两类请求均未拿到它。

这是现有事实保护规则，不能通过把所有研究记忆自动标为用户已确认来解决。需要评估如何让 agent 按需回看自己的未验证判断、尝试和反证，同时保留候选标识、原来源和任务归属。优先复用原记录，避免再复制一套“探索账本”。

## 已有能力与本轮不下的结论

- 连续调度、无变化等待、失败恢复和任务终止已有实现；此次相关确定性回归通过。
- 必要追问和任务结束已有复核，不能说系统完全没有纠偏能力。
- 实质新颖度、重复想法识别、商业判断质量和主动换方法的可靠性，不能由合成回复证明。本轮没有宣称这些已经通过真实模型评估。
- 先补可用信息与读取通路，再评估模型能否合理使用；不把没有依据的效果问题归咎于某个模型，也不增加商机类型或固定业务流程。

## 后续实现：工作上下文与按需回查

实现计划见 [agent-context-recall](superpowers/plans/2026-10-27-agent-context-recall.md)。复用原数据库、任务状态和执行引擎，无新的任务模式、配置表单、业务字段或依赖。

- 规划获得开轮已选择的有效记忆与最近三份工作记录；规划和生成均获得开轮保存的最近三条成果反馈。反馈保留对象版本、accept/revise 与原文，不自动改成永久偏好。
- `search_task_context`、`read_task_context` 绑定实际运行的联系人/任务，支持已保存成果、有效记忆、当前任务来源的研究候选及历史反馈。每页最多 6 个 300 字摘要或 6000 字正文；使用游标/偏移续读，不把全部历史塞入每次模型请求。
- 默认查本轮固定成果版本的累计分节，也可指定更早版本核对修改前的正文；禁止读更新版本。反馈固定开轮上界。模型生成的候选研究保留 `candidate` 和来源 run，不改成 active；不开放其他任务的候选、其他联系人或 session 私聊记忆。
- 接单及其纠正仍无工具；工作规划仅有当前任务回查工具。生成可使用回查与原有授权执行工具。回查属于内建能力，不依赖启用技能脚本；工具禁用列表仍有效。
- 实际交给模型的检索摘要/正文记录来源引用，后续阶段可据引用再次读取。引用去重且有上限，恢复时继续核对。记忆纠正/忘记、运行取消/暂停、来源丢失会阻止提交；忘记记忆及删除来源任务还会取消依赖运行、登记持久清理并清理执行缓存。
- 原稿修订仍走已有 `sectionId` 选择与完整分节读取校验；回查不是扩大写入或共享资料权限的途径，也不算本轮新外部证据。

### 失败→修复与独立审查

新测试先复现缺失回查模块、规划无记忆/无工具；补齐后两种引擎实际执行三类检索与正文读取，再生成并保存含来源的成果。关闭脚本工具仍可回查，重开数据库后快照和引用保持。既有共享成果测试暴露规划数据拼接回归，已保持原结构化数据段并通过 33 项回归；既有工具边界断言改为只允许两项只读工具，仍拒绝未授权执行。

独立审查发现：默认累计成果查询不能定位被覆盖的旧版本正文；已增加显式历史版本检索。另发现删除来源任务只会阻止其他任务旧结果提交、未及时取消/清理依赖运行；已用受支持的旧记忆迁移场景复现，再在同一事务内失效依赖引用，命令层取消并等待受影响运行后清理。审查者复验确认无剩余阻塞发现。
