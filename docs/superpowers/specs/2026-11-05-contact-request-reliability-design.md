# 联系人任务请求追踪与可靠性

依据：用户同意借鉴 Superagent 的消息归属、处理追踪、契约测试，并明确要求开始实施。产品约束仍以 `docs/contact-task-spec.md` 为唯一入口。

## 代码核查与缺口

| 链路 | 已有证据 | 本轮需补齐 |
| --- | --- | --- |
| 聊天路由 | `agents/chat-changes.ts` 以 latest 为当前请求，校验真实任务 ID，歧义追问，有界修复 | 路由使用随机工具调用 ID，不能作为跨重试的用户请求身份 |
| 任务修改 | `agents/tools.ts` 的 feedback 命令校验设置/任务版本；`contact/mutations.ts` 同事务保存要求、取消旧轮次 | 通用任务请求缺少独立原文、会话、稳定请求 ID、处理回执；内存 consumed 无法跨重启 |
| 确认 | `action-interactions.ts` 持久卡片及执行开始标记；不确定副作用不重放 | 确认后的工具准备缺少原始请求来源，不能把模型 reason 当作用户原文 |
| 成果反馈 | `feedback-ledger.ts` 已关联反馈、重试轮次、实际成果版本 | 复用它的事实语义；通用要求修改也需关联后续轮次及实际结果 |
| 执行 | `contact/scheduling.ts` 保存轮次输入；`workloop/model.ts` 为共同模型调用边界 | 把已保存要求的请求快照绑定到轮次，记录实际模型输入交付证据，不能以排队冒充处理 |
| 交付 | `contact/completion.ts` 原子保存正式成果、进度、通知；旧轮次 assertLive | 在同一事务关联请求与真实成果版本；结束但无成果必须如实展示 |
| 查询 | 任务互动和需求日志可查看；历史不补造 | 提供有界分页请求记录，复用互动记录视图与现有成果/轮次入口 |

## 方案与边界

采用现有 SQLite 任务库内的请求账本，接入现有工具、命令、调度、成果提交。相比只加日志，它能保证幂等和事务一致性；相比移植 Superagent Engine，它保留原生/DSH、现有调度及 UI。此实现选择由开发方作出，用户未要求引入新引擎。

- 原始来源由宿主从当前用户消息构造，含请求 ID、会话、可验证时的消息 ID、原文、接收时间；模型不能填写来源。历史、引用和工具结果只提供参考。
- 重试和继续回复沿用原用户消息身份；编辑版本持久化，编辑重发（包括改回原文）与另发消息分别接纳。来源链接只在已保存消息正文及编辑版本匹配时提供；未带消息身份的旧调用按原请求编号去重。
- 同一用户请求的任务写操作只能被接纳一次；重复相同负载返回保存事实，身份相同但操作不同则拒绝。不同消息可顺序补充同一任务，旧版本冲突仍拒绝，不盲目合并完整字段。
- 要求及账本同事务保存，提交后才取消执行/通知。保存失败不产生成功回执；未接纳的普通聊天不排入任务队列。
- 明确区分保存、关联轮次、发往模型、轮次状态及正式成果版本。发往模型不证明模型理解或语义落实；正式成果关联也不冒充逐条要求验收。
- 任务已暂停/结束时修改要求仍保持状态。旧轮次不得覆盖新要求。正常重启只恢复既有任务执行，不重发普通聊天，不重放外部副作用。
- 新记录保留原始来源；旧数据来源未知，不根据历史反推。只读查询核对联系人/任务归属，使用稳定游标、有界分页。删除沿用任务数据删除规则。
- 自然语言单输入、共同任务 UI、独立联系人、成果正文引用、主动未读闪烁全部保持。

## 验收

使用真实 SQLite 与真实命令/工具，模型外部调用可用确定性夹具：连续补充、同请求重放、冲突负载、跨联系人、错误版本、多任务歧义、引用不授权、暂停保留、确认前后来源、保存/执行/提交三个重启窗口、迟到结果、结果事务失败及分页。模型接口测试检查实际注册工具和参数，而非仅搜索提示词原文。类型检查、边界检查、相关专项及全量单测分别记录；不把夹具通过写成在线模型或长期运行验收。
