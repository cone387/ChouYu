# 任务成果设计师 Agent

日期：2026-11-06。状态：设计草案，尚未实施；等待设计确认后编写实施计划。

## 1. 意图与已确认范围

用户希望有一位专门的 Agent，了解 ChouYu 当前 UI，读取其他联系人的正式输出，编程创作适合内容的成果展示界面。范围明确为每项任务的“任务成果”区域。正式成果自动交给设计师，不要求用户逐项点击。用户明确允许移除原来作者联系人自己修改展示的逻辑。

用户随后明确：不要兼容旧机制。新设计直接替换作者自定义展示，不保留旧展示读取、执行、导出、主题兼容或旧工具兼容转发；旧展示请求不迁移成新设计任务。原作者正式成果正文及其来源继续保留，新设计师以正文为输入重新设计。

目标是让设计师真正完成理解内容、设计、编程、预览和修正，而不是给现有 Markdown 增加几个样式选项。小说、研究、想法与评审可以采用不同的信息组织方式。正文仍来自原作者保存的真实成果。

不改 App 全局导航、任务编辑表单、聊天布局或执行引擎；不新增探索模式、任务类型选择、多选或批量操作。遵循 `docs/contact-task-spec.md` 的共同任务 UI、单描述弹窗、直接交付正文、真实来源及主动消息未读闪烁要求。普通聊天输出不等待设计师完成，也不逐条调用设计师重写消息。

## 2. 方案与选择

此前讨论的两种触发方案是：用户手动指定需要设计的任务，或正式成果保存后自动接手。用户选择自动接手，并明确撤去作者自行修改展示的职责。

实现沿用“共同阅读容器＋每项任务独立设计”的讨论方向：设计师可使用公共基础样式和工具，也能自由编写 HTML/CSS/JavaScript。固定模板只能作为它可复用的资源，不成为唯一输出形式。任意修改整个 App 不符合用户已限定的范围。

以下身份、调度与发布细节属于本设计的工程建议，未冒充用户已经逐项指定；不兼容旧展示机制属于用户明确要求。

## 3. 设计师身份与执行职责

- 提供一个稳定的内置设计师联系人，暂用名“界面设计师”；有独立身份与公共交流规则，不借用 ChouYu 身份。沿用资料、模型配置、工作设置和工作记录入口，不新建设置面板。
- 专职职责通过明确的能力标识绑定，不能仅凭联系人名称或人设文本取得跨联系人读取、设计发布权限；普通联系人不能通过模型参数冒充设计师。
- 自动设计使用既有 Harness、取消、用量结算、全局执行名额与退出屏障。复用 AgentSpace 模块边界承载设计工作，不另建模型执行引擎，也不把设计工作伪装成作者的一轮研究或正文修订。
- 首次创建联系人时沿用当前默认 Provider 配置策略；不静默创建密钥、更换付费服务或提升额度。缺少配置、视觉能力或额度时保存待处理状态，用户仍能立即阅读正文。
- 设计师并发建议首期为 1，与全局执行名额共同约束。设计师可以通过已有工作设置暂停自动处理。暂停不删除待处理设计、不暂停作者写作；恢复后合并处理最新有效输入。
- 内置身份与生命周期的具体代码组织由实施者根据现有角色创建机制确定，必须保持重启不重复创建，并提供明确的停用能力。

## 4. 成果范围、数据归属与权限

系统为每次设计建立不可伪造的工作范围：任务域、任务 ID、作者 ID、源成果版本/正文指纹，以及展示请求修订号。工具参数不能扩大范围。

- 默认只读该任务正式保存的正文、目录、来源、文件元数据及新机制下设计师已生成的展示。旧作者展示代码不作为输入。其他任务、私聊、密钥、未经共享的记忆均不作为默认上下文。
- 用户确认的自动设计授权仅提供这项职责所需的正式成果读取，不给设计师通用的跨联系人代答、写任务、恢复执行或修改正文权限。
- 需要额外关联成果时，沿用已授权的共享来源并保留固定版本。来源权限在读取、预览与发布前复核；撤权或删除应取消在途工作并使相应引用失效。
- 数据通过宿主提供的只读接口获取。生成页面不能自行枚举其他任务、访问文件系统、请求网络或调用 Electron/Node。
- 所有显示的作者正文必须绑定原成果。图表只能使用真实来源中的数据；没有数据就不生成数值。设计师新增的摘要/说明必须标明属于展示加工，并可返回原文，不替代或改写原作者正式成果。

任务域按现有 TaskCenter 能力适配：联系人版本化成果直接适配；ChouYu 安排的已保存执行结果使用实际执行 ID 与内容指纹建立可回查快照，不伪造既有历史版本。没有正式结果的用户待办、普通状态更新、接单计划和空结果不触发设计。具体适配入口在实施计划中逐一核查，不以“其他域不支持”作为永久例外。

## 5. 自动接收与持续更新

正式成果持久化成功后产生设计待办；事务回滚、流式草稿、计划和进度摘要不能触发。需要以持久 outbox/唯一键实现接收，跨数据库域的来源采用各域提交后可重放事件或增量补查，不能依赖易丢失的 renderer 事件。

建议幂等键为来源身份＋源版本/指纹＋展示请求修订号＋设计环境版本。同一事件重试不会重复创建设计或重复扣除已结算调用。设计师自身保存展示不再次触发正文成果事件，避免递归设计。

- 第一次有正文：立即进入队列，原文立即可读，不阻塞作者交付。
- 作者继续更新：每任务最多保留一个执行中工作及一个最新待处理目标。新版本不不断打断运行造成饥饿；当前工作可以完成验证，但只有仍适用当前目标时才可启用，旧目标只作为历史候选保留。
- 新机制下设计师已经生成的设计尽量复用。宿主先绑定新数据做适用性预览；正文覆盖、目录定位或交互验证失败，或存在结构/展示要求变化时，才请求设计师修改代码。不能把先前验证结果直接用于新正文，也不读取旧作者展示。
- 需要稳定 DOM 或版本引用的设计必须声明数据绑定契约。即使代码不变，新的源版本也生成独立的验证/绑定记录，不冒称旧页面已审核了新内容。
- 用户提出展示要求时，保存原话和来源、递增请求修订号；这类显式修改优先于自动更新。旧请求结果不能覆盖新要求。
- 来源任务暂停时不自动启动新设计，已有页面仍可读；明确提出一次展示修改可只处理保存的固定版本，不恢复作者任务。来源任务完成不禁止展示处理，因为最终成果仍需设计；删除/撤权取消工作。
- 重启恢复区分排队、执行中断、验证中断和已发布，不能因不知道结果而重复发布。超时、取消和退出需要等待模型与预览资源实际释放。

已有成果正文建议采用惰性接入：升级时不为全库历史成果集中调用模型；用户打开某个任务的成果，或该任务产生新正式成果时，自动登记当前最新正文版本。在新设计可用前显示普通正文，不再展示旧作者页面。此策略只影响已有正文的首次设计，新成果始终自动接收，不要求用户手动选择。

## 6. 给设计师的 UI 环境

提供一个版本化、可读取的设计环境说明，而不是只附一句“跟随系统主题”：

- 当前共享主题 token、字体、字号、间距、默认表单及键盘规则。
- 成果区域的真实可用宽高、嵌入方式、深浅主题与窄窗约束。
- 成果读取契约、正文/文件/来源表示、允许的交互和引用锚点。
- 可复用的基础组件/片段及其使用方法，不强制套同一种成果模板。
- 新机制下已有的设计代码和实际渲染截图；首次设计提供普通正文与容器截图，不加载旧作者页面。参考截图仅捕获成果容器和必要宿主边界，不采集用户桌面、其他聊天或无关页面。

首期用现有原生 HTML/CSS/JavaScript 能力，不增加运行时外部依赖下载。是否引入构建后的组件运行时留给以后，不作为完成本轮的前提。

## 7. 编程、预览、检查与发布

设计师必须能够按需读取完整成果（长内容分页），不能把目录或摘要当成已理解全文。调用读取与实际提供的范围留痕。展示可基于稳定数据接口呈现任意长度正文，不要求把全量长文塞入一次模型输入。

设计工作循环为：读取来源及 UI 环境 → 编写候选代码 → 在与正式阅读器相同的沙箱中渲染 → 获取截图和结构/运行诊断 → 操作检查 → 修正 → 保存并应用。

预览是产品内部能力，不依赖本次 Codex 会话的桌面连接。宿主提供受限预览会话和截图/点击/滚动/键盘测试工具，只能作用于当前候选页面；不能操作其他应用或可信宿主控件。预览使用独立、可终止的执行上下文，脚本死循环、资源超量、超时或取消不得拖住主 UI。渲染窗口不自动抢焦点。

发布前必须验证：

1. 代码结构、脚本语法和资源限制；无不允许的网络、父页面或系统访问。
2. 正文数据完整绑定；导航可以到达全部分节，不以透明、裁剪或固定截断掩盖缺失内容。分页/折叠允许，但必须能展开、导航并回到原文。
3. 窄宽视口和深浅主题均有真实渲染记录；无页面级横向溢出、遮挡主要操作或不可读正文。
4. 存在的目录、折叠、筛选等交互实际操作通过；引用与来源定位仍对应真实版本。
5. 设计师读取实际截图及诊断后完成视觉复核；不能以 JavaScript 编译通过冒充视觉通过。当前模型不支持图片时明确阻塞视觉验收，不默默发布未看过的页面。

建议每次工作最多 3 轮代码候选，使用现有预算、总时限和取消规则；具体时限在实施计划结合现有模型延迟设置。失败保留原文或新机制中已验证且匹配来源的上一版设计，以及错误与重试入口，不回退到旧作者展示，不无限循环。自动修复耗尽后等待明确重试、配置恢复或新版本，不每次轮询重新生成。

通过检查后自动启用，无需每次用户审批。必须在提交时再次核对来源、请求修订号、权限和任务存活状态。当前正在阅读的页面不被热替换；出现新版入口，由用户切换或下次重新打开时使用。不能将旧版展示绑定到未经验证的新正文。

## 8. 正文与展示分开版本化

保留现有正式正文版本，不改写历史。新增独立的展示记录，至少包含：

- 所属任务、设计师身份、设计版本、代码及内容哈希。
- 固定来源列表与版本/指纹、展示请求修订号、设计环境版本。
- 候选/已验证/已启用/失败或失效状态，以及实际检查证据。
- 执行关联、真实用量、时间和失败原因。

已启用指针只在验证和最后版本校验通过后切换，新机制中设计师的历史设计版本可恢复。恢复适用于同一固定来源；跨源版本须重新验证，不提供恢复旧作者页面的入口。正文版本、设计版本、数据绑定版本在内部明确区分，日常阅读不堆叠内部编号。

展示修改不调用作者正文 `finish()`，不增加正文版本、不改变任务完成状态、不生成虚假的作者交付，也不重复投递原文。底层保存方式可以沿用现有 SQLite/不可变代码块，但具体表名交由实施者决定。

## 9. 阅读区域与修改入口

仍由共同任务成果组件和共用阅读器承载，无 ChouYu 专用分叉。设计师控制成果内容区域；系统保留可信的来源、原文、展示恢复和版本操作边界。生成页面不能伪装系统确认或改变权限。

作者成果在设计完成前正常显示原文。设计工作状态在结果区域简明可见，不用状态卡代替成果；失败不会将原成果显示为写作失败。展示生效通知由设计师发出并关联来源任务，按既有可靠投递、去重和未读闪烁规则处理，不重复发送作者全文。

“修改阅读样式”改为向设计师提交自然语言要求，仍使用现有弹窗规范。用户在作者聊天中提出页面/布局修改时，宿主转交设计师并返回真实受理回执；作者不再执行展示编程。正文改写仍由作者处理，混合请求分清两种职责并保留来源，不把展示修改解释为重写正文。

简单字号、间距等确定性阅读偏好可以由宿主即时处理，不为每次点选调用模型；后续“表达要求”仍属于作者内容偏好，不随展示职责迁移。不得将这些已有偏好误删或新增任务设置多字段。

现有强制覆盖所有子元素背景/文字/阴影的主题逻辑替换为宿主边界样式与设计 token 契约；生成页面使用 token 并在深浅主题实际验收。删除旧作者页面的主题兼容分支。

## 10. 直接替换作者展示机制

需核查并移除作者展示生成、修改和旧展示消费路径：

- `agent-delivery-instructions.ts` 中首次写作提供 `presentation` 的要求，以及写作/研究工作流的相应注入。
- 作者工具目录中的 `revise_contact_presentation` 执行能力和 `presentation-revision.ts` 作者运行路径。
- `chat-changes.ts`、阅读器按钮、修订弹窗中直接把展示修改作为作者任务修订的路由。
- 正式正文提交对新的作者 `presentation` 写入权限；只改提示词不算职责迁移完成。
- 旧成果 `presentation` 的读取展示、脚本执行、HTML 导出、主题适配和旧页面恢复入口；通用沙箱实现可重构复用，但只能服务新设计契约。

历史 `presentation` 不读取、不执行、不导出、不转成设计师页面，也不作为设计参考。新的作者模型意外返回展示字段时不得保存或执行该代码；可恢复的正文按既有有界协议纠正处理，不能静默认可作者仍有设计权限。

旧作者样式队列、运行和待确认操作直接停止或标为失效，不转换成新设计请求、不重放、不设置旧工具兼容转发。正在运行的旧工作取消并等待退出，迟到结果不得提交；旧卡片引用已移除能力时通过通用失效处理明确无法继续，不能伪造转交成功。新设计工作只由正式正文接收或新机制下的用户展示要求产生。

旧作者 `presentation` 字段从新成果读写契约中移除，不为旧字段、旧 API 或旧页面维护适配层。新展示只通过设计师独立权限和契约保存。移除旧展示机制不删除作者的正式正文、正文版本、文件或来源证据；已保存正文统一使用普通正文阅读器及新设计师展示。

## 11. 验收与文档同步

确定性/故障验证覆盖：自动接收事务窗口、去重、更新合并、无递归、来源隔离、暂停/恢复、结束任务的最终设计、删除/撤权、额度阻塞、退出与重启恢复、过期结果拒绝、旧队列停止失效、旧展示无读取执行路径，以及正文版本不受样式修订影响。以包含旧展示字段的已有成果验证正文仍完整可读，旧脚本不会执行或进入设计师输入。

真实 Electron 验证覆盖：生产同容器预览、脚本错误与失控清理、深浅色/窄窗、所有正文可达、引用/目录交互、原文回退、正在阅读不被替换、作者与设计师聊天路由。验证是实际交互和存储核对，不能只有截图或接口夹具。

质量样例至少包括长篇写作、研究报告、多个想法、评审结论。检查真实内容理解、信息层次、阅读与查找体验；记录失败样本、用量与等待时间。模型视觉检查不是客观美观证明，需要人工看图与使用复核。不宣称一次样例代表所有任务，也不恢复用户取消的全天长测门槛。

本轮不因设计稿存在声称代码完成。实施时同步 `docs/contact-task-spec.md`、`docs/contact-custom-deliveries.md`、`docs/current-status.md` 与专门验收记录；现行规范中的作者展示职责以本次用户明确变更更新，注明旧机制已移除，不再保留“兼容旧作者展示”的能力说明。

## 12. 实施前需要核实的工程事项

- 联系人身份初始化、已有默认配置与模块挂载方式；最小设计工具权限集合。
- 各成果域事务与持久事件入口，尤其助手执行结果跨库重放；恢复/删除顺序。
- Native/DSH 后台实际图片输入能力、预览截图工具的传输与用量边界；不假定所有已配置 Provider 都支持视觉。
- 隔离预览的 Electron 运行/销毁机制及可以确定性执行的正文覆盖检查。

这些应通过源码核查和有针对性的能力验证落实到实施计划，不由用户重新选择技术细节。任何无法满足的关键能力必须登记并解决，不能默认为用户批准降级。

已核对的具体差距：`workloop/model.ts` 当前后台调用构造的是纯文本 prompt；`harness/dsh/background.ts` 的模块能力声明为 `images: false`。因此本轮必须补齐设计工作到实际视觉模型的截图传输与能力检查，不能只加截图工具名称就声称设计师看到了页面，也不能因 DSH 尚未接通而静默换引擎。Native/DSH 支持范围分别实测并记录；不支持的配置明确阻塞并保留可阅读正文。
