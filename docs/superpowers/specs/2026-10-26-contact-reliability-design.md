# 联系人可靠性与持续运行优化设计

日期：2026-10-26。状态：设计草案，尚未实现；待用户审阅。

产品权威仍为 [联系人任务规范](../../contact-task-spec.md) 与根目录 AGENTS.md。本设计是本轮实现附件，不建立第二套产品规范。基线为 master `dc5894e`。

## 1. 目标与已确认方向

用户要求按本次架构评估继续一轮优化，并专门讨论共享 worker 是否应拆分。讨论后的推荐方向是保留共享 worker；用户回应“嗯”，本设计据此沿该方向展开，不推定用户要求任一联系人进程故障时其他任务绝不中断。

本轮覆盖六项：存储恢复与备份、运行可观测性、长期查询/同步成本、明确的任务结束条件、模型语义回归、职责与文档整理。按可靠性 → 性能 → 行为与回归的顺序实施，不能只完成第一项便声称整轮完成。

结果应让用户能判断联系人为何等待、故障后保留哪些工作、备份能恢复什么；明确安排的结束条件由程序执行；历史增长时避免反复读取和同步全部正文。

保持既有单描述弹窗、共同任务 UI、独立身份、原任务恢复、固定成果正文、权限/额度、全部主动消息未读闪烁。用户待办的日期重复规则不变，不增加快速新建、多选或批量操作。退出/休眠期间不宣称继续执行。

## 2. 承载方案与选择

| 方案 | 价值 | 成本 | 本轮决定 |
| --- | --- | --- | --- |
| 共享 worker + 联系人逻辑隔离 | 低常驻开销，保留现有调度、存储和协作事务 | 进程级故障影响全部后台工作 | 采用；加强诊断、恢复、测试 |
| 固定 worker 池 | 限制故障影响范围，可控制进程数量 | 需要任务领取、跨进程额度与依赖协调；同库仍是共同依赖 | 不在本轮实施 |
| 每联系人独立进程 | 按联系人重启和故障隔离 | 开销、连接和管理随联系人增长；分库又引入跨库协作 | 不在本轮实施 |

普通模型/工具错误和异步等待继续按联系人/任务处理，不因单个 RPC 超时杀掉健康 worker。保留独立 ping、进程代际校验、有限重启、同任务取消后等待真实退出。共享宿主是明确设计，不再列为必须修复的缺陷。未来若实测需要执行进程池，保留共享协调与持久化的演进方向，但本轮不预建空抽象。

## 3. A：运行状态与恢复诊断

### 3.1 状态权威

主进程持有宿主状态：未启动、启动中、就绪、恢复中、不可用、关闭中。状态由真实启动/RPC/退出事件推进，包含单调代际与修订号；旧进程消息不得修改新进程状态。

只读快照包含：最近启动/就绪时间、最近成功同步、重启次数与最近原因、已知活动名额、待投递数量与最老待投递时间、备份状态。worker 不可用时未知字段为未知，保留上次观测时间，不用零或旧的运行状态冒充实时值。

诊断仅保存事件种类、代际、匿名请求标识、阶段耗时、数据库角色/阶段/SQLite 码等必要元数据，不记录凭据、模型正文、资料内容或私有地址。采用有大小/数量上限的本地日志；成功重试不覆盖原失败。事件循环延迟、同步耗时、队列等待与执行耗时分别测量。

启动/同步/通知失败从无说明的 catch 转为记录和状态更新，仍保留原重试边界。显式“重试连接”只重建通信/宿主，不自动重放结果未确认的修改命令；健康宿主不被重复启动。不得将延长超时或增加无限重试作为修复。

### 3.2 用户呈现

在现有联系人工作区域和共同任务概览呈现简短异常说明及原失败入口；详细诊断按需展开。就绪时不加常驻大面板，不把技术心跳转换成联系人聊天消息。任务读失败停止运行图标，宿主恢复不切换用户正在阅读的任务/成果。

助手安排从 AssistantRoutineService 的实际执行状态提供只读快照，内置问候/回来从实际检查/生成状态提供快照，休息提醒仅在真实发送阶段记录。按能力适配进共同任务状态和工具栏，不移入 WorkLoop、不计入持续任务名额。对不支持中断的瞬时阶段不伪造暂停按钮。

## 4. B：联系人备份与恢复保护

### 4.1 范围和发布

联系人任务 `agents.db` 与 LangGraph `checkpoints.db` 作为同一备份组，清单记录组 ID、时间、schema 版本、文件哈希和校验结果。应用库、附件、技能库、DSH SDK 原始会话不属于此组；界面和文档明确它不是整应用备份。

工程默认：有持久变更后每 5 分钟合并一次备份请求，保留最近 3 个完整有效组，首次初始化成功且已有业务数据时安排首份备份；正常退出在服务停写后尝试最终快照。频率/保留数是内部工程常量，不增加联系人配置字段。报告最近成功时间与连续失败，不承诺 5 分钟内一定能取得安全快照。

快照期间停止新任务领取和外部工具发起，在图步骤持久边界停放执行；等待已有业务提交和 checkpoint 写入完成，再以同一屏障下的两个数据库快照生成一组。执行中模型返回结果可等待屏障释放后再提交，不能取消、丢弃或重复调用。所有业务写入口（任务命令、调度、成果、checkpoint、清理等）必须参与屏障，不能只暂停 tick。等待安全边界最多 30 秒，超时记录备份延期、保留上一有效组，释放屏障让工作继续，不杀进程换取备份。

使用 SQLite 一致性快照 API，先写临时组并校验，再发布完成清单。只识别有完整清单且全体校验通过的组；半写入组不覆盖上一有效组。完整性和外键、任务/轮次/检查点归属检查分别记录。快照或轮转失败不删源文件，不阻止已成功持久化的业务结果。删除旧备份只作用于经绝对路径校验的本功能专属目录。

### 4.2 恢复语义

正常 worker 崩溃仍从当前数据库恢复，不回滚到备份。WAL 映射暂未释放、权限问题、磁盘满、较新 schema 均不得被误判为损坏并自动替换数据库。保留现有精确错误码的三次有界重开，新增诊断与故障注入，不声称已解决未知句柄根因。

确认数据损坏/缺失后保持业务停写，在原存储故障入口展示可用备份时间及回退范围。只有用户明确选择恢复才替换；恢复前保留完整原文件族，关闭全部相关连接，按可恢复的步骤记录发布过程。恢复中再次崩溃应能继续或回退到原组，不能得到混合代际的两库。没有有效组则保持故障，不创建空任务库冒充恢复。

备份之后发生过的模型用量、删除、工具副作用和 DSH 会话不能由旧快照证明。恢复后进入持久化的“需要核对”保护：不自动领取旧任务、不自动续跑旧 checkpoint、不重发旧待投递消息、不退还已知消耗。先与当前应用角色名单、持久消息回执及可用 SDK 归属记录核对；缺失角色不复活。用户明确恢复单项工作前须说明可能回退的记录；未知外部操作仍禁止自动重放。旧任务/成果可以只读查看；恢复备份本身不等于授权全部任务继续。

完整数据目录备份仍有必要，自动任务备份不替代独立设备备份。DSH 原始执行日志未包含在备份组内，不声称任意 SDK 会话可从旧备份无损续跑。

### 4.3 解除恢复保护的具体范围

恢复保护由备份组之外的应用库保存，并绑定恢复组及联系人/任务；主进程和 worker 的读取/调度入口均检查。应用库也不可用时不得开始联系人备份恢复。该记录不是消费账本，也不声称能证明备份之后发生过的全部操作。

恢复的成果、记忆、资料、交接与权限先作为“恢复后待核对”的只读历史供用户查看，不进入模型上下文、共享目录、自动交接或新任务输入。当前应用角色名单仍为身份权威；旧库内共享/权限不因恢复而自动启用。新任务同样受到联系人恢复保护，不能绕过它读取可能已撤回的资料。用户核对后按单联系人、单任务或单资料的既有入口解除相应范围，范围外仍保持隔离，不新增批量任务操作。

用户明确继续任务后，仅能从已核对的正式成果、当前要求与当前授权创建新恢复尝试，保留旧轮次供审计，绝不执行备份中的在途工具指令或旧 checkpoint。存在未核对外部副作用的任务仍阻塞写操作：通用“继续”不能替代实际结果核对。用户可记录已核实的操作结果；无法核实时维持阻塞，不能提供“仍未知但自动再试”的旁路。只读续作也必须先满足资料、任务和额度核对条件。

### 4.4 恢复后的额度

恢复快照内的已消费和未知预留继续保留。若当前原库/运行记录可以可靠核对更多消费，按稳定调用身份合并，不重复相加，也不使用模型推测。不能可靠确定备份之后消耗的联系人进入“恢复后额度待核对”，覆盖旧任务和新建任务；不把缺失消耗记为零，跨日只刷新正常每日维度，不清除未知累计消耗保护。

确实无法补齐时，用户可在真实阻塞卡片明确授权“从本次恢复起额外允许”的调用/Token 额度，沿原每日与单任务两层限制检查，持久记录恢复组、授权范围和后续消耗。该额度是新增授权，不是返还旧额度或覆盖历史账单；旧累计用量保持“不完整”，已知消费仍保留。单任务累计不明时需单任务授权，不能只提高联系人每日额度便绕过。重复提交同一授权返回原回执。恢复当前任务库再次失败时，新授权记录仍留在应用库，须先核对才能继续，不能由旧快照重新取得同一份额度。

## 5. C：长期数据与同步成本

先建立同机基线：1/8/24 联系人，短/长会话，10/100/300 成果版本。记录启动耗时、主/后台事件循环延迟、内存、每轮身份扫描量与 RPC 字节、备份耗时及查询耗时；同参数比较，不用不同夹具宣称性能提升。

### 5.1 联系人身份增量同步

把身份快照构造从 agents/index 拆到专用模块。资料、默认模型、人设、工具授权、密钥版本、技能版本、会话正文变化、已投递来源、删除和模块装卸均有明确失效来源。每个联系人单独维护版本；只发送变更联系人，worker 新代际仍全量同步。

近期真实对话只读取原有范围，自动通知继续排除。保存确认后再前移已同步水位，失败重试不丢变更；并发修改只确认实际发送的版本，不能把随后变更标为已同步。保留周期补偿，但无变化周期不遍历每条历史消息。权限撤回继续及时生效；当前轮次的执行快照、技能和引擎选择规则不变。

### 5.2 会话查询与加载

应用库逐步成为会话元数据和正文查询的直接来源：启动读取会话元数据，正文按选中会话/所需上下文加载，历史分页用稳定消息位置和 ID 游标。共享会话缓存需有上限及脏数据保护；保存失败时不得逐出唯一未保存副本。现有编辑重发、附件、消息来源、未读、草稿和迟到响应保护保持一致。

搜索改为数据库查询/索引适配，保留原有 Unicode、子串匹配、顺序、结果限制和点击定位语义；先为实际查询建立索引与有界候选读取，不擅自用分词命中替代子串行为。需要新增规范化列/索引时做可恢复迁移，旧应用版本屏障与当前数据格式一致。

应用库周期备份评估并采用当前 SQLite 驱动的异步分页备份接口，保留“验证、发布、保留旧备份”的契约。退出须等待正在发布的快照完成或明确失败，不能先关连接。备份期间的新写入保留 dirty 水位，不被旧快照成功清空。

成果正文块方案保留。300 版清单增长单独测量；本轮仅做有证据的索引/缓存调整，不为降低清单字节引入另一套成果格式或删除历史。

## 6. D：明确的任务结束条件

仅自然语言入口，复用新建/编辑/聊天的实际保存服务。保存原话、解析时刻、时区和可核对的来源片段；模型只解析，归属、版本和范围由程序校验。未提及的结束条件保留，明确撤销才移除。已有任务没有可靠结构化期限时不从旧摘要猜补，仍沿原结束核对工作。

### 6.1 截止时间

支持明确日期/时刻与有明确起点的持续时长。日期截止按本地该日结束处理，持久化为下一日零点的排他边界；精确时刻按该瞬间，不在之后发起新模型/工具步骤。相对时长以本次要求首次持久接受时间锚定，重试或只改名称不能推迟期限。“全天/24h持续工作”仍不等于“仅工作24小时后结束”；相对起点/时区有歧义才追问。

到期停止后续执行，在共同状态中显示“已到截止时间”，与“目标达成”分开。已发出的模型/工具请求在安全返回点结束，不硬杀不可撤销操作；已产生结果完成原有校验/必要持久化，不追加纠正模型调用或新工具执行。需额外调用才能通过校验的候选保留为未交付草稿，不假报完成。到期时仍待用户回复的轮次停止自动推进，保留原问题和截止原因。

重启/唤醒时先检查期限，再决定是否恢复请求。到期后普通“继续”解释期限并沿单描述入口修改，不能悄悄删掉期限；明确用户修改并继续才恢复。暂停任务到期也记录调度结束，但不抹掉原暂停记录。

### 6.2 次数与期次

本轮支持明确的“成功交付/提醒 N 次（期）”上限，计数单位是日历期次的成功持久交付，重试同一期不重复计数、失败/取消不计成功、消息回执重放不重复计数。多时刻一天有多个独立期次；只补最近一期的现有错过日程规则不变。联系人和助手安排分别在各自域事务中提交计数、期次完成和结束原因。

提交点按成果与提醒的实际能力明确区分：联系人写作/研究的“产出/交付N期”在正式成果和待投递记录同事务保存时计数，第N期消息暂未送达也停止新开期次，原消息继续沿 outbox 重试；助手“提醒/发送N次”在消息持久送达后凭稳定回执计数。助手重启遇到“消息已送达、状态未记账”时先查询原回执，再原子更新期次计数/历史/结束状态，不重新生成或发送。为此给助手域提供应用库事务端口，不能依赖当前多次独立 write 的偶然顺序。

若用户明确要求联系人“发到聊天N次”，其规则采用送达计数，并在第N期结果已准备但未送达时阻止继续开第N+1期；源域通过已有消息回执确认补记，仍无跨库事务。若只说“成功交付”且上下文无法辨别保存或送达，澄清提交点。次数规则持久保存计数模式与稳定期次身份，读取/UI显示对应的“已产出/已送达”，不能混成一个含糊的完成数。

截止后允许补送截止前已正式保存的待投递正文，也允许已在途请求安全返回后合法保存的结果沿原回执投递；截止不撤销已产生的成果交付。不得为补送再生成正文、再开期次或越过用户后来暂停通知/撤权/清空消息的边界。备份恢复的旧 outbox 仍受第4节的恢复核对保护，不能套用普通重试规则自动发送。

裸“执行 N 次”可能表示尝试次数或成功次数；无法从上下文确定时只追问这一点，不擅自宣称支持两种语义。普通非日历创作中的“十章/十个 idea”仍是内容目标，继续由已有成果/完成核对处理，不按内部 run 或模型调用数量结束。

修改总成功次数保留历史累计，明确“从现在再做 N 次”以保存时累计量为基准建立新目标；更改日历时计数不意外清零。已有历史无可靠期次计数时只允许明确“从现在再做”或追问，不从报告数量推算。截止与次数并存时以先达到的调度终点为准，仍不表示内容质量已验收。

## 7. E：模型语义回归

扩展已有 test-contact-model 和 contact-live 矩阵，不另建生产模型审查链。记录源码版本、执行引擎、模型标识、场景、首次通过/纠正通过/失败、实际调用与 Token（未知明确标记）、耗时和脱敏失败类别。

固定场景：聊天草稿与正式成果修订分流；编辑重发使用新目标；完整任务不重复追问；实际读取固定来源后评审；正文篇幅真实核对；明确截止/次数解析保存；持续任务不提前结束；失败后的原反馈与引用保留。程序断言检查实际持久化和最终正文，不只断言路由选择。质量抽查独立记录，不把有引用或运行结束当作事实正确。
