# ChouYu 系统迭代与模块收敛设计

状态：用户以“ok”确认书面设计；进入实施计划编制，尚未实施。基线：`ef40294`。日期：2026-10-22。

## 目标与范围

用户已确认“按你的建议都迭代好”。本设计覆盖整份建议，不将完成定义缩减为目录搬迁或第一批拆分：工作区与 IPC 分域、公共消息交付、三域任务契约、联系人任务存储职责、大历史存储、成果反馈修订、依赖唤醒、失败接续和当前文档校准。

保留 Electron 本地应用、现有 AgentSpace / ContactAgent / WorkLoop / Harness 架构。应用退出或休眠期间不宣称工作。用户已经取消的 24 小时长测和跨日等待不作为本次门槛。采用分批可验证的模块化单体，不引入微服务、每联系人独立进程、第三方状态框架或新的数据库依赖。

权威产品规则为 `AGENTS.md`、`docs/contact-task-spec.md`、`docs/task-scheduling.md`。现有功能不能因本次重构回退。以下各子项目独立实施、独立回归，最终按全范围验收。

## 不变量

- 联系人和 ChouYu 安排继续共用任务列表卡片、详情导航、工具栏、概览及任务弹窗；任务新建和设置均为单描述输入，必要信息缺失才补问。
- 用户待办、联系人工作和助手安排保留各自语义、数据库及执行引擎。日期重复按日程独立生成每期任务。
- 所有角色共用交流规则与来源契约，人设独立。交付引用保存正文，不新增逐消息润色调用，不以内部进度字段代替正文。
- 所有主动消息保留同等未读闪烁；送达、已读、待处理是不同状态；重试不能复活用户清空的消息。
- 成果、任务进度与待投递记录同事务提交。取消等待真实执行退出，迟到结果不能覆盖已编辑、暂停或删除状态。
- 不新增快速新建、批量处理、多选任务、今天页过期提示或筛选条件标签；不改变表单焦点装饰及无关页面布局。
- 数据迁移不能删除源数据来绕过失败；保存失败可见，保留重试和恢复能力；不把短时夹具测试当成真实模型或全天验证。

## A. 应用边界与界面职责

### IPC 与聊天应用服务

将 `src/main/ipc.ts` 的注册职责按聊天、会话/角色、记忆、配置/供应商、捕获、桌面平台分域。新增 `src/main/ipc/` 中的域注册模块，中央入口只装配依赖和注册域。

聊天应用服务持有请求注册、取消、工具确认和模型执行生命周期；IPC 仅解析请求、校验来源、调用服务及发送事件。服务通过明确端口读取配置和会话、使用 ContactAgent.Chat；不得重新绕过 AgentSpace 执行普通聊天。关闭面板继续请求、关闭应用清理请求、显式停止取消请求三种语义保持分离。

preload 按域组织 bridge，但继续暴露同一个 `electronAPI` 兼容产品调用。共享契约仅依赖共享类型，不反向导入 renderer、Electron 或具体服务。

### 工作区与任务页面

新增 Workspace 容器，承接页面切换、页面保活、全局搜索、来源跳转和返回位置。聊天页面只负责会话、消息和输入区。会话生成状态继续使用现有 `useSessionWorkspace`，不得因页面卸载取消后台聊天或丢失待确认工具。

弹窗协调负责顶层关闭、Esc、返回焦点和桌面鼠标穿透；业务弹窗保留原组件。来源跳转统一经过类型化导航请求，并在目的端复核归属、版本和存在性。

`TasksView` 将数据刷新/查询、单任务命令、列表呈现及弹窗草稿拆成有职责的模块。保留现有筛选排序工具栏、自定义视图和单任务操作；不复制一套联系人任务 UI。

增加依赖边界检查：shared 不依赖 main/renderer；任务中心不依赖 renderer；领域服务不依赖 IPC 注册；新工作区容器不让业务页相互导入。以实际 import 图检查，旧依赖若暂时保留需具名登记且不能增加。

## B. 公共消息交付

新增 `src/main/messaging/`，负责统一交付请求、来源核验、幂等落库、回执结果和未读广播。业务方仍持有触发规则与正文生成；各域自己的待投递记录继续属于原事务。

交付请求使用可区分联合：助手消息、联系人正式通知、交互卡片。携带稳定 receipt ID、owner、来源引用和已保存正文；不同来源不得借用对方身份。收件会话和来源归属在落库前核验。

成功顺序：源域事务提交待投递记录 → 接收端持久提交消息与幂等回执 → 更新未读/广播 → 确认源域回执。广播失败不能使成功消息重复写入；接收落库失败不确认源域。用户删除消息仍保留必要的已送达标记，不因源域重试重建消息。

联系人后台、助手安排/问候工作检查、待办提醒、稍后提醒和 renderer 主动消息均实际调用此入口。复用当前 append 和回执语义，避免创造第二个消息事实来源。不宣称跨库事务或外部副作用恰好一次。

## C. 类型化任务契约

保持 `{domain, owner, id}` 引用。为 todo、assistant、contact 定义命令参数元组与返回值映射；TaskCenter 的 bind/execute/list/read 保留具体域类型。联系人 RPC 使用相同命令映射，不继续在业务调用点扩散 `string`、`any` 和 `unknown[]`。

未知输入在 IPC/RPC 边界验证，类型约束不替代运行时验证。错误域、未知命令、归属不符、过期版本、已卸载域均拒绝。业务校验仍由原域执行，避免复制规则。可用编译断言证明错域参数和返回值错配不能通过。

## D. ContactTaskStore 职责拆分

`ContactTaskStore` 保留组合与公共兼容入口，逐步委托：

1. 查询投影：dashboard、summary、overview、详情/指标与互动分页。
2. 额度账本：调用预留、释放、任务预算、实际请求计费及搜索额度；复用已有 Token 预算实现。
3. 调度仓储：日程、可运行选择、失败退避、恢复及轮次创建。
4. 任务命令：创建、编辑、回答、继续、删除及版本校验。
5. 结果提交：正式成果、进度、记忆处理、依赖事件及待投递记录的单一事务边界。

各模块共享原连接和明确事务上下文，不私自打开另一个库，不各自提交原本原子的操作。查询模块不能执行命令。避免用一个万能 Store 接口把所有方法重新传给每个子模块。

## E. 存储规模与迁移

### 测量

用隔离数据测量 1,000 / 10,000 / 50,000 条消息的保存、查询、启动加载、主进程事件循环停顿及磁盘占用，记录机器与运行环境。成果测量 10 / 100 / 300 个逐章增长版本的正文存储量、固定版读取及导出。测量脚本不读取真实用户数据、不调用付费模型。

2026-10-22 文件写入预检：实际 `writeStoreFile` 路径在 50,000 条合成消息下，单条修改仍需约 258–320 ms 同步保存，而 1,000 条约 9–10 ms。这已支持以 SQLite 增量仓储作为优先设计；完整 database/Electron 链路及优化对比仍为实施验收项，不能用预检代替。方法和范围见 `docs/system-evolution-acceptance-20261022.md`。

### 聊天增量持久化

抽离会话/消息仓储与配置/角色/偏好存储。若基线证实全量同步写入随历史增长明显放大保存成本，则使用现有 better-sqlite3 将会话、消息和送达回执增量持久化；只更新变化消息及必要会话元数据，配置偏好不再带着全量历史落盘。运行时采用单一写入权威，不做两份实时双写。

迁移流程：读取并验证旧存储 → 在独立目标事务写入和核对数量/ID/正文/来源/已读/回执 → 记录完成标记 → 切换读取。旧文件保留恢复副本；失败不得标成功或切换到半成品。已有损坏隔离、新格式保护、附件独立存储和保存失败 UI 保持。明确防止旧应用静默覆写新格式。

现有消息追加在保存失败后保留内存消息和回执用于重试。新仓储必须显式区分待保存状态与持久提交状态，保留重试正文、拒绝提前确认源域，并防止重试再插入一条；不能把“有内存回执”等同于已经落盘。

若基线没有支持迁移的性能证据，记录数字与判据，仍完成仓储分离和增量保存接口，不以未经验证的性能判断强迁移；最终报告说明实际采用方案及原因。

### 成果版本正文去重

使用不可变正文块与版本清单。正文块按内容哈希寻址，版本清单保存章节顺序、标题、正文引用、所属 run 和已有版本元数据。对外仍返回原 `AgentDelivery`，固定版查看、引用校验、修订和 Markdown/HTML 导出保持一致。

旧快照在事务中迁移，先核对重建结果再替换旧行。缺块或损坏必须报错，不能当空正文。任务删除清理无引用块，跨版本仍引用的块不能删除。相同正文复用不等于合并联系人权限；权限继续由 owner/topic/version 校验。300 版逐章追加的唯一正文存储应随唯一正文量增长，而非累计全量快照增长。

## F. 交付反馈与修订闭环

扩展现有 `contact_delivery_feedback`，把反馈关联到实际修订请求、run、基准版本及完成后的成果版本。保存反馈和入队修订同事务；失败、取消、等待和完成来自真实轮次，不能由 UI 猜测。

成果与互动界面复用已有组件展示“对第几版的意见、修订状态、实际产生哪版”，支持打开基准版及结果版。accept 只记录认可，不结束持续任务；revise 不自动扩大预算或权限。重复提交使用稳定请求键防重，过期成果版本明确拒绝。旧反馈没有因果记录时显示未关联，不倒推补造。

## G. 成果依赖唤醒与失败接续

### 依赖

在现有持续交接与已授权实际来源读取上登记显式依赖，不根据模型文字猜测。来源成果事务提交时记录可恢复更新事件；调度端按依赖找到候选任务、核对当前读取/共享权限、任务状态、工作时间和额度，然后决定可运行性。

持续交接允许跟随后续版本；一次性交接和固定版引用不暗中跟随最新版。按章节正文指纹去重，只有阅读样式或无关章节变化不重复评审。事件合并到仍未处理的最新相关版本，不把所有中间版本排成无限队列。事件不能跳过用户明确的固定执行时间、暂停、待回复、手动工作模式或预算限制。周期检查继续作为漏事件恢复补偿。

### 接续

将现有网络退避、权限恢复、预算等待和进程恢复的可恢复原因投影成共同的恢复信息；各域仍决定原状态转换。共用任务操作和现有失败卡片提供准确的继续路径，保留任务描述、原始反馈、版本与检查点。

瞬时网络故障按现有有界策略恢复；权限重新启用和预算恢复只让原本允许自动工作的任务重新具备资格，不自动重启用户暂停任务。未知外部执行结果不能自动重放。显式重试绑定当前版本及稳定请求身份，避免重复任务或重复交付。恢复不切走正在阅读的任务。
