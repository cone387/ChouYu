# 持续探索：赚钱机会首场景

日期：2026-10-27。状态：设计草案，已完成独立可实施性检查，待用户确认；尚未实现新能力。

现行产品约束仍以 [联系人任务规范](../../contact-task-spec.md) 为准。本文件细化下一轮候选能力，不表示已启动真实任务或完成市场调研。

## 1. 已确认的需求与设计建议

用户希望联系人主动提供想法，并能持续推进；首个场景是寻找赚钱的点子。用户明确同时接受技术产品与技术以外的生意，只要存在赚钱机会，不限定为 AI 产品或软件项目。本轮讨论重点是持续工作的功能体验。

本设计建议先完成“单联系人持续探索 + 想法沉淀”，复用已有反馈、成果修订和联系人交接。赚钱机会是第一个验收场景，探索能力本身面向任意用户指定主题。

不推定用户的资金、所在地、客户资源、时间或团队规模。不因为缺少这些偏好阻止初步探索，也不自动过滤所有有投入门槛的机会；把每个方向所需条件写清楚，只有进入具体执行且信息确实必要时才追问。

## 2. 路径比较与推荐

| 路径 | 收益 | 代价与适用范围 |
| --- | --- | --- |
| 在现有持续任务中增加探索策略与持久探索记录（推荐） | 复用调度、暂停、恢复、任务 UI、正文交付和来源；能解决跨轮重复与方向选择 | 需要补齐模式识别、机会记录和规划输入，通用工作流须保持兼容 |
| 只扩写 Idea 实验提示词并开放入口 | 实现量较小，能快速演示生成与评审 | 提示词无法保证记录、去重、来源和反馈持续有效，开发实验的角色/时间设定也不适合普通任务 |
| 首版默认安排生成、评审等多个联系人 | 能提供独立视角，已有共享成果机制可复用 | 增加配置、权限和协同复杂度，不能代替单个探索者的持久记录 |

推荐第一条。独立评审作为后续增强，通过已有交接选择使用，不自动创建联系人或把多个角色强加给所有探索任务。此处架构取舍是实现建议，用户明确确认的是探索范围和持续产出诉求。

## 3. 用户入口与看见的结果

沿用现有联系人聊天建任务或普通“新建任务”弹窗，仍只有一个任务描述。例如：

> 持续帮我寻找有希望赚钱的点子，技术产品、服务和其他生意都可以。讲清楚谁付钱、为什么付钱、怎样找到第一批客户。核查有价值的方向，记住已经提出和排除的想法，找到值得尝试的机会继续深入。

任务解析保存通用探索策略及原始要求，用户不需要填写任务类型、行业表、评分权重或额外表单。普通有限请求“给我五个赚钱点子”仍是有限任务，不能据“赚钱”关键词启动长期探索。

探索策略决定工作内容，不自动改写联系人级工作方式。自动且连续推进的联系人在本轮提交后接续；间隔推进按已保存间隔运行；按需联系人沿原接单流程完成首轮后等待手动继续。接单回执必须解释实际生效方式，不能在按需状态声称已经开始自动连续运行。需要调整工作方式时复用现有工作设置/配置交互事项，明确这是联系人级变更及对其他任务的影响，由用户沿原入口确认；创建探索任务本身不隐式执行该变更。此选择优先保留已有设置契约，不新增任务级调度引擎。

同一任务可先发现多个不同方向，再选择值得核实或深入的候选。聊天直接收到保存的想法正文或实质更新；探索目录和候选来源在既有任务成果中可回看。不增加独立任务面板、快速新建或批量处理。

用户仍通过聊天或现有成果反馈表达“继续查这个”“这个方向不考虑”“这个条件我做不到”。第一版复用现有引用及任务修改机制：明确对象时关联具体想法，指代不清且会影响不同机会时才澄清。不得靠生成页面中的脚本虚构能修改宿主状态的操作按钮。

## 4. 持续推进规则

每轮从原任务要求、已保存探索记录、最近实际反馈和允许访问的证据中选择下一步：

1. 发现不同的机会：寻找新的付费对象、问题、交付方式或获客渠道。
2. 核查候选：查找支持与反对材料，说明是否存在实际需求线索及竞争替代。
3. 深化候选：形成可尝试的获客切入点、交付方案和最小验证办法。
4. 比较与调整：依据新增材料保留、搁置或排除方向，保留理由。

这些是探索动作，不要求每个想法机械执行所有步骤，也不固定“每八轮复盘”等产品节奏。模型选择动作与理由，宿主负责验证引用、权限、归属、版本和是否实际提交。

有新的机会正文、证据或实质修订就按既有连续调度继续。某一候选受阻时可以推进其他候选或另开方向；只有整体没有可推进内容、实际失败、必要追问或既有运行规则阻塞时等待。发现机会与深化机会都不能长期垄断调度：规划输入包含长期未深入候选与近期反复选择记录，模型需解释继续同一方向的新增目标。

产出一个或一批点子不等于整个探索任务结束。用户明确的有限目标、截止、暂停与恢复沿用现有契约；“持续”不自动变成只运行一天，也不意味着绕过已有权限与运行限制。应用关闭期间不声称后台仍在工作，重启按已有恢复机制接续。

## 5. 赚钱机会的正文要求

每个可交付机会至少解释：

- 具体客户及其付费理由；当前解决方式和替代选择。
- 提供什么产品或服务、可能怎样收费、如何触达第一批客户。
- 所需技能、渠道、投入、资质或合作条件；未知条件明确保留。
- 已查到的需求线索和反证、关键假设、主要失败风险。
- 最小验证步骤、观察什么结果、什么结果意味着应该换方向。
- 与本任务已有机会相比，实质差异是什么。

范围包括技术与非技术方向；行业分类由实际内容产生，不固定成用户必须选择的清单。优先级建议依据付费路径是否具体、证据强弱、客户是否可触达以及验证成本说明，不能把模型评分包装为盈利概率。

估算收入、成本和回本条件时列明假设或可核对来源，不能把模型推测标为事实。搜索结果、竞品存在、有人抱怨和真实付费是不同强度的证据；已验证需求必须对应真实验证材料。首版产出研究与验证方案，实际对外执行沿原工具权限及用户授权进行。

## 6. 探索记录与去重

首版采用“通用探索记录 + 赚钱场景附加要求”，支持非商业主题作为兼容验收。通用候选保存对象/问题/方案/适用条件与证据，不要求非商业任务填写客户或收费信息；赚钱场景在此基础上增加客户、付费方式、获客路径等受校验的附加内容。场景由原任务要求决定，不能因为正文提到钱就自动切换任务场景。

在联系人任务库保存有界字段的候选索引，与正式成果分节和不可变版本关联。索引不再复制一份长篇正文。赚钱场景称为“机会”，其他场景使用任务本身的名称。建议的最小概念：

- **候选/机会**：稳定 ID、所属联系人/任务、标题、对象、问题、方案、适用条件、当前判断、理由、最近更新及正式正文引用；赚钱场景另含客户、交付与收费方式、获客路径。
- **方向决策**：继续、暂搁或排除的原因、来源（用户明确意见或 agent 判断）、发生时间与依据引用。用户排除与模型暂搁必须可区分。
- **探索动作**：本轮发现/核查/深化的对象、简短理由、实际证据引用、是否产生新正文；复用既有轮次记录和来源 ID。

检索先取相关候选与简短目录；需要判断细节时读取对应正式正文，不每轮加载全部历史。候选检索和分页不能把未加载的历史当作不存在。

语义去重是有证据的判断，不承诺数学意义上的全局唯一：按对象、问题和方案检索近似项（赚钱场景结合客户与交付方式），再由模型说明“新增”或“既有机会的变化”。完全相同正文沿现有指纹机制阻止重复投递。只是换标题或换说法不能计为新机会；已有机会增加证据或改变方案时更新原 ID、产生新版本。用户要求保留的不同地区/客群方案可作为有明确差别的变体关联原机会。

用户排除的方向在后续规划中作为持久约束；有了新证据可以说明变化并征询是否重看，不能自动撤销用户排除。agent 自己搁置的候选可在新证据到来后重新评估，记录原因。

## 7. 保存、恢复与失败行为

机会索引、正式成果更新及对应探索记录同属一个业务提交；任一失败全部回滚，不出现目录有条目但正文未保存。只有正式正文保存成功才投递，沿用来源契约和持久回执。单纯更换内部状态、反复自评或扫描无变化不发成果消息。

同一轮重试必须幂等；同一机会继续使用稳定 ID；暂停、删除、任务修订或来源失效后，迟到的模型结果不能写入。恢复引用固定版本，不能自动换成最新正文。删除任务按原删除范围清理探索索引；每日已发生消耗保留本轮架构加固行为。

用户反馈和下一轮选择须读取已提交的方向决策；反馈写入失败保留输入、明确未生效。并发反馈按任务版本验证，不能静默覆盖。

无自主搜索权限/凭据时可以继续提出明确标为假设的候选、设计验证步骤或使用已授权材料；不能声称联网查证。任务明确要求完成在线验证而能力不足时，复用既有配置/权限交互事项说明阻塞。只检查未保存新正文不宣称已交付新点子。

## 8. 与现有实现的衔接

| 现有入口 | 建议改动 |
| --- | --- |
| `src/main/workloop/result-contracts.ts`、`workflow.ts` | 接单结构承载可选探索策略；规划与交付携带受校验的机会引用、动作与结果；保持普通研究/创作兼容 |
| `src/shared/agents.ts`、任务创建/编辑路径 | 保存任务策略和原始要求；只有明确持续探索的请求才启用；编辑遵循原版本与暂停契约 |
| `src/main/task-center/contact-store.ts`、分责 Store | 探索索引/决策迁移、查询与原成果事务集成；历史任务保持现状，不把旧正文自动加工成已验证机会 |
| `src/main/agents/delivery.ts`、`feedback-ledger.ts`、已有聊天路由 | 固定成果引用、机会定向反馈和幂等提交；复用实际修改服务 |
| `src/main/task-center/contact/scheduling.ts` | 复用现有连续推进、无变化等待和公平调度；避免新增第二套定时循环 |
| 共用任务成果界面与正文投递 | 回看真实机会及版本，复用现有详情和反馈；允许按成果特点排版，不另造任务 UI |

`src/main/agents/idea-lab.ts` 是仅开发模式启用的双联系人、限时实验；不把其固定身份、固定目标、限时或实验配置迁入正式用户任务。

具体字段、检索索引、单轮上下文大小和文件拆分由实施者根据现有类型与读写成本决定，属于实现选择。初版不以新增向量库或独立进程为前提。

## 9. 验收

涉及既有 SPEC 的 FORM、RUN、MSG、HIST、SCOPE 约束，实施计划需映射原第 11 节验收编号。新增场景：

- EXP-01：一句话创建技术与非技术均可的持续赚钱机会任务；不增加表单字段；有限“五个点子”不转为无限任务。
- EXP-02：连续多轮包含不同机会、既有机会核查与深化；保存后继续，首个点子/一批点子不误结束任务。
- EXP-03：已有机会换标题不计为新条目；增加有依据的差异保存为原机会新版本；跨重启保留排除原因。
- EXP-04：明确指向某机会的继续/排除反馈影响后续规划，其他机会仍可推进；不清楚指向时不猜错对象。
- EXP-05：证据可定位到真实读取内容和版本；无搜索权限时不伪造搜索或验证，不编造付费与盈利事实。
- EXP-06：机会索引/成果/轮次提交失败全部回滚；重试不重复生成已提交机会或重复发消息。
- EXP-07：暂停、删除、编辑、重启和故障恢复保留现有取消、占位、来源及幂等语义。
- EXP-08：大量历史机会下，规划只加载有界相关上下文，检索仍能找到较早机会；可重复测量查询和写入增长成本。
- EXP-09：普通写作、有限研究、独立评审、定时安排及已有反馈路径不因探索策略改变。
- EXP-10：自动连续、自动间隔、按需三种联系人设置下创建任务，实际调度与回执一致；创建任务不改变其他任务的工作方式。
- EXP-11：非商业主题使用同一探索策略完成候选发现与深化，成果不被强制填入客户、收费、获客字段；赚钱场景附加要求仍有效。

确定性测试验证状态、归属、事务、来源和调度；合成模型验证端到端控制流。实际模型抽测另行评估新颖度、事实边界和方案可尝试程度，不能用字段完整或模型自评分代替质量证据，也不能把研究验收写成赚钱效果保证。

## 10. 交付范围

首版交付通用探索策略、机会索引与方向决策、受权限约束的核查/深化、原 UI 中的创建/阅读/反馈，以及回归和能力边界文档。独立多联系人评审沿已有功能可用，自动组队与额外商机工作台不列为首版新增要求。

已有完整桌面冒烟的启动等待、窗口交互验收缺口继续登记于 [架构加固验收](../../architecture-hardening-acceptance-20261027.md)，本设计不将其视为已解决。
