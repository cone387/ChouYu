# ChouYu 内置 Harness 与统一模块接入设计

日期：2026-10-16。状态：方向已获用户确认；本文待书面评审，尚未实施。

## 1. 用户目标与本轮交付

用户希望将 ChouYu 自己的执行流程正式做成内置 Harness，与已接入的 DeepSeek Harness 并列，降低继续迭代的成本。用户进一步明确：本项目按新项目设计，不考虑旧架构兼容。因此本轮直接迁移调用方，删除旧包装、旧名称和兼容入口，不以保持旧调用方式为设计约束。

交付是一套实际使用的内置模块接口、完整的原生执行模块和通过同一接口接入的 DSH 模块。每个联系人继续在现有资料编辑弹窗选择引擎，保存后下一次普通聊天生效；进行中的请求固定使用开始时选定的引擎。

本轮不新增插件商店、外部代码动态加载或第三套设置页面。后台任务、日记与主动消息的模型调用迁移到新的原生执行基础，但不在本轮将后台调度改为按联系人选择 DSH。原有产品能力及其验收要求保留，不把清理旧代码等同于删除功能。

## 2. 当前代码证据

- `src/main/harness/legacy.ts` 仅包装 `streamAIChat`；原生工具循环、供应商协议和网络流均在 `src/main/ai.ts`。
- `src/main/harness/coordinator.ts` 已管理请求取消和事件序号，但硬编码了 DSH 平台判断与错误文案。
- `src/main/ipc.ts` 直接选择 DSH 工具白名单、确认回执模式、日志刷新、失效清理和消息保存确认。
- `src/main/agents/service.ts`、`assistant-routines`、`journal` 等也调用 `streamAIChat`，其中后台任务依赖每轮预算钩子及输出上限。这些调用方需要同步迁移，不能留下第二份旧循环。
- 当前持久化引擎标识为 `legacy | dsh`；新定义为 `native | dsh`，不保留 `legacy` 别名或双协议。

## 3. 方案选择

采用“原生执行模块 + 静态模块注册 + 公共宿主服务”。它将执行逻辑真正归入 Harness，接入新执行器时主要增加模块，而不是继续扩展 IPC 条件分支。

仅给现有包装改名不能解决 `ai.ts` 和 IPC 的耦合，不采用。把模型执行、后台任务调度、权限和消息保存全部搬入插件会让每个执行器重复实现业务，本轮也不采用。

## 4. 职责划分

| 层 | 负责 | 边界 |
| --- | --- | --- |
| ChouYu 宿主 | 联系人身份、有效配置、记忆/资料/引用、权限、业务工具、确认卡片、成果与消息保存、未读送达 | 所有执行器调用同一套真实业务服务 |
| Harness 注册与协调 | 模块选择、能力检查、请求生命周期、事件顺序、取消、终态、生命周期分发 | 不依赖 DSH 类、数据库结构或具体工具名称 |
| ChouYu Harness | 原生模型请求、工具循环、流输出、用量、执行中止 | 不拥有联系人数据库或任务调度器 |
| DSH Harness | SDK 运行时、DSH 输入适配、执行日志、回执等待、恢复与清理 | 保留已验证的 SDK 和持久化边界，通过模块接口与宿主合作 |

这里的“插件”是随应用发布的可信内置模块，不是允许加载任意第三方代码的安全边界。

## 5. 原生模块与调用迁移

新增 `src/main/harness/native/`：

- `index.ts`：原生模块描述及 Harness 运行入口。
- `runner.ts`：唯一的原生多轮执行循环，负责轮次上限、逐轮钩子、工具结果反馈、取消及最终完成。
- `providers/openai.ts`、`providers/claude.ts`：各协议的消息编码、工具调用解析、单轮流式请求与工具结果编码。
- `providers/request.ts`：流读取和请求超时管理。

共同的执行类型置于不依赖 Electron 或业务数据库的类型模块。各供应商提供单轮请求及会话编码接口，循环只实现一次，避免两套轮次控制逐渐分化。

删除 `legacy.ts` 和 `createLegacyAdapter`。从 `ai.ts` 移除 `streamAIChat` 及其执行实现；`ai.ts` 只保留供应商模型列表和诊断能力。所有源码、测试和 smoke 调用方直接使用新原生入口或公共 Harness 入口，不新增旧名称 re-export、兼容 facade 或按版本分叉。

原生执行保持这些具体能力：OpenAI-compatible 与 Claude 协议、各自现有图片编码、最多 6 轮、工具结果回传、逐轮预算检查、输出上限、用量回调、流中断与取消。现有供应商协议适配（例如端点明确拒绝工具定义或 usage 字段时的处理）属于仍需提供的模型接入能力，不因删除工程兼容层而移除。

后台任务继续在每次真实模型轮次前检查预算，实际请求结束后释放对应轮次占用；取消、预算不足或上下文失效后不能多发下一轮。日记和主动消息使用同一原生执行基础，保留自身的总时限、长度限制和业务规则。

## 6. 模块契约与能力

模块由稳定 ID、显示名称、能力描述、执行适配器以及需要时的生命周期钩子组成。静态注册处是唯一组合 `native` 和 `dsh` 实现的地方。IPC 不导入具体适配器或 DSH 服务。

能力描述至少包含支持平台、执行场景、输入类型、工具允许范围、持久确认方式及恢复能力。能力声明必须被执行入口使用，不能只是说明文字：

| 能力 | native | dsh |
| --- | --- | --- |
| 本轮普通聊天接入 | 支持 | 支持 |
| 平台 | 原应用支持平台 | Windows |
| 图片 | 按原生供应商支持的编码传递 | 拒绝，不静默丢弃 |
| 工具范围 | 宿主授权且当前可用的工具 | 再取资料读取、读取输出偏好、设置输出偏好三项交集 |
| 持久确认 | 发送原卡片，返回待确认结果 | 日志持久化后发送原卡片，等待实际保存回执 |
| 崩溃后执行结果恢复 | 不声明支持 | 从已提交记录恢复，不重新推理 |

能力只收窄权限，不能授予权限。工具暴露和实际调用均校验允许范围，模型即使自行编造未提供的工具名也不能越过限制。权限实时撤销仍由公共工具服务执行校验。

确认方式作为执行期绑定对象提供给公共工具服务，包括必要的持久化前置钩子和回执等待函数。自然语言配置路由仍先由公共宿主处理；在路由尚未进入 Harness 前，不启用 DSH 回执机制。不能依靠非空断言访问尚未准备完成的 Harness 输入。

恢复、数据清理、消息保存确认和关闭统一通过模块生命周期接口分发；具体 DSH 日志、租约和表结构留在 DSH 模块内。启动恢复仍先检查真实记录，普通原生聊天不得为了注册而启动 DSH 子进程。

## 7. 事件、失败与持久化

两种模块输出共同事件：开始、文本 append/replace、用量、工具执行状态及唯一终态。协调器统一添加请求 ID、尝试 ID 和递增序号；流发送与终态处理不按引擎名称分支。供应商的增量累计用量按同一轮请求标识更新，不把多个流片段相加计费。

工具事件区分正在执行、等待用户、完成和失败。发送了确认卡片只代表卡片已发送，不代表业务操作已执行；业务成功仍取实际写入回执。公共卡片与原有工具 UI 复用，不为 Harness 新建第二套确认界面。

取消后不得再发起模型请求或业务写入；迟到文本与终态不能覆盖已取消请求。失败不自动切换引擎，不自动重放可能已产生副作用的调用。清理失败不能吞掉原执行错误或阻止协调器释放活动请求；需保留可重试清理状态并准确报告。

模型/权限/引用的有效性由宿主校验。每轮及最终交付前检查上下文，DSH 仍保留有效配置变化后的失效保护。单纯切换联系人的引擎选择不改变已开始请求。

消息保存继续使用公共服务；DSH 的稳定消息来源与日志确认保留。原生不能伪造持久日志来源或声称具备崩溃恢复。本轮不新增原生执行日志数据库。

## 8. 新项目命名与设置

源码及当前测试中的原生引擎 ID 统一改为 `native`，默认值、联系人校验、自然语言设置 schema、UI 选项和 smoke 夹具一并迁移。历史文档保留原事实，不为了全文搜索消除历史中的 `legacy` 字样。

不为 `legacy` 加别名、特殊读分支或专用数据迁移器；非法显式引擎输入按现有校验模式报错，未设置引擎的联系人使用当前默认 `native`。不得为了清理名称删除真实用户数据、会话或 DSH 运行记录。

入口仍为“联系人 → 详情 → 编辑 → 聊天执行引擎”，包含 ChouYu 原生和 DeepSeek Harness（实验性）。不新增环境变量选择方式；不修改无关 UI、任务单描述约定或未读闪烁。

## 9. 验收要求

| 编号 | 可证明的完成条件 |
| --- | --- |
| NH-01 | 原生执行实现从 `ai.ts` 迁出，工具循环只有一份；所有调用方直接使用新入口；无旧包装、旧函数别名或 `legacy` 引擎分支 |
| NH-02 | OpenAI-compatible 与 Claude 的文本、图片、工具多轮、用量、超时、6 轮上限及逐轮预算行为通过协议级回归 |
| NH-03 | 两模块通过同一注册/协调接口运行；IPC 无 DSH 适配器调用、工具白名单或按引擎名称判断的执行逻辑 |
| NH-04 | 平台、输入、工具限制在执行前生效；直接构造越权工具调用也被拒绝；原生请求不启动 DSH |
| NH-05 | 事件序号、唯一终态、取消、迟到输出、失败不回退及清理失败释放请求通过双引擎契约测试 |
| NH-06 | 原生与 DSH 的确认语义均准确；DSH 拒绝、重复点击、等待中停止不重复写入；路由阶段不误入回执等待 |
| NH-07 | 联系人独立选择、保存失败、切回原生、请求中途改选择及应用重启保存通过回归；实际 Electron 界面完成切换和聊天验证 |
| NH-08 | 后台任务预算钩子、日记及主动消息调用迁移后回归通过，后台调度没有被引擎设置意外切换 |
| NH-09 | DSH 已提交结果恢复、保存确认、联系人/会话清理及关闭行为回归通过；既有未完成发布验收不被写成已完成 |
| NH-10 | 类型检查、全量测试、应用构建通过；独立代码审查问题处理完毕；更新架构、产品实现状态及本轮验收记录 |

测试以本地确定性模型协议、实际工具/卡片服务和 Electron 验证为主。未经实际调用不声称真实供应商通过；此前的在线额度、完整跨库强杀、严格断网与 NSIS 安装向导等未完成门槛，仍以 `docs/dsh-harness-acceptance-20261015.md` 为准。本轮模块化既不消除这些门槛，也不要求重复构建未改动的 DSH 依赖包。
