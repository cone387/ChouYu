# 工作日志接入方案（建议稿）

日期：2026-09-07。本文记录架构方案与分阶段实施进度；不代表已开启用户活动记录。

实施更新：活动时间线初版已在工作区实现，记录默认关闭。实际范围和验证见 [工作日志初版](work-journal.md)。下文中的截图、OCR、AI 分析等仍为后续方案。

## 选择：内置可选模块，独立后台执行，预留适配接口

用户直接使用“工作日志”，无需先安装插件。默认不记录；用户开启后可在托盘暂停，关闭日志窗口不停止已开启的后台记录。采集、分析、数据保留分别配置。

代码作为独立 journal 模块维护，不向 ChatPanel 或主 ipc.ts 持续堆叠实现。不把采集定时器放在 renderer；当前主窗口开启 backgroundThrottling，且日志生命周期不应依赖聊天页面挂载。

### 现有插件为何不适合作为第一版宿主

- `src/main/plugins/types.ts` 的 PluginDefinition 以 execute(content)、认证和 init 为核心，没有完整的停止、暂停恢复、常驻任务及数据生命周期契约。
- `src/main/plugins/registry.ts` 当前静态注册内置 BBTalk，不是成熟的第三方后台服务安装平台。
- `src/main/capabilities/registry.ts` 当前只支持 memory-engine 与 embedding，不能直接声称已支持采集插件。
- `src/main/capabilities/process-transport.ts` 已有进程隔离、环境过滤、超时和消息限制，但方法白名单及请求响应协议不直接适用于持续采集事件。可提取通用部分，不应让日志伪装成记忆引擎。

内置是分发和产品入口选择；独立进程是运行方式；可替换接口是代码组织方式。这三者可以同时成立。

## 接入点与职责

| 层 | 建议位置 | 职责 |
| --- | --- | --- |
| 类型 | src/shared/journal.ts | 配置、状态、活动、证据、分页查询、事件版本 |
| 协调 | src/main/journal/service.ts | 启停、暂停原因、系统事件、队列调度及资源预算 |
| IPC | src/main/journal/ipc.ts | 严格校验查询范围、记录开关和删除操作 |
| 数据 | src/main/journal/storage.ts | 独立 journal.db、迁移、事务、分页和保留策略；由专用 worker 执行重查询/写入 |
| 采集 | src/main/journal/capture/ | 随包分发的 Windows helper 适配、进程管理、活动事件、媒体索引 |
| 分析 | src/main/journal/analysis/ | OCR 与模型队列，失败重试、取消、分析版本和预算 |
| 桥接 | src/preload/index.ts | 暴露类型化 journal API，不向 renderer 开放任意路径读取 |
| 界面 | src/renderer/src/components/Journal/ | 日志时间线、证据详情、搜索与采集状态 |
| 聊天 | src/main/tools/registry.ts | 受范围约束的日志搜索与片段读取工具 |

`src/main/index.ts` 负责创建服务并在退出时停止采集、收尾媒体和数据库。helper 不继承 AI 密钥；媒体经受控目录传递，IPC 只传有界元数据与 ID，不持续发送 base64 图像。

第一版采用独立的常规日志窗口，复用 React 和主题 token；不强塞进当前透明、置顶、承担桌面宠物交互的主窗口。日志窗口关闭时销毁或隐藏界面，后台服务按用户记录状态继续运行。提供单实例窗口管理，避免多个时间线重复加载。

入口：聊天顶栏“工作日志”、托盘“打开日志/暂停记录”、`/journal`。设置导航直接增加“工作日志”，不隐藏到高级设置折叠项中。首次页展示用途和开启按钮；正常进入默认展示当天时间线。

## 数据与状态

独立 userData/journal 目录，包含 journal.db 和 media；不会将截图放入聊天 JSON 或长期记忆数据库。工作日志可单独清空、设置保留期限和迁移。

表建议：activity_events、captures、ocr_documents、analysis_jobs、observations、journal_entries、entry_sources。原始来源和派生内容使用稳定 ID 关联，模型生成内容保留版本。OCR 可重建，全文索引需验证中文查询效果。

对外状态包含 enabled、pauseReasons、helperHealth、lastCapturedAt、pendingAnalysis、storageUsage。手动暂停、锁屏、空闲和错误为不同原因：解除锁屏不能顺带解除手动暂停。关闭功能时停止采集与后台处理，不删除已有数据；采集暂停与分析开关单独展示。

采集会话使用 epoch：暂停/禁用后旧 epoch 的晚到画面拒绝落盘。对已删除时间范围增加取消与版本检查，避免正在分析的任务重新生成已删除日志。只有实际收到采集心跳才展示正常记录；失败时展示缺口，不能填成用户空闲。

截图落盘、数据库索引和文件清理需设计恢复流程；磁盘不足时暂停采集并提示，不能仅删除尚未分析数据后宣称记录完整。

## 可替换能力边界

第一版仅实现需要的内部接口：CaptureAdapter（Windows 采集）、FrameStore（压缩图片，后续可增加编码分段）、Analyzer（本地 OCR/可选视觉模型）。不先建立通用插件市场。

后续适合扩展的能力：浏览器来源采集、Git/文件变更来源、其他 OCR/分析 Provider、日报导出目的地。暂停规则、存储所有权、保留期限和删除由宿主统一管理，不交给各插件自行决定。

工作日志转为长期记忆需要明确的提炼动作；聊天搜索日志只取相关时间范围和片段，不默认上传整天记录。第一版不让模型修改原始证据。

## 最小交付切分

1. **模块基础与活动记录**：独立数据库和窗口、默认关闭、托盘控制、前台活动/空闲/锁屏事件、可见错误与重启恢复。
2. **关键画面与搜索**：周期采集、变化去重、后台 OCR、时间/应用/关键词检索、截图详情、排除规则及完整删除。2026-09-07 工作区实现收窄为仅保存前台窗口，不采集整个屏幕；窗口内部字段不自动遮蔽。当前使用 JPEG 精确去重及 OCR 子进程，未实施视频分段和感知去重。
3. **日志分析与聊天**：异步片段总结、日报、日志搜索工具、来源跳转和重新分析；模型能力单独诊断，不能假设聊天 Provider 支持视觉。
4. **性能与打包收敛**：一天运行记录、休眠恢复、多屏变更、helper 崩溃、磁盘满、离线队列和删除竞态；根据结果决定媒体分段编码。

前两步交付后即能验证找回价值，不依赖云端模型。后台分析必须限流，不抢占用户主动聊天。完成各阶段后再调整默认采样参数，不承诺未经实测的 CPU、磁盘和费用数值。

参考：[Dayflow 源码分析](work-journal-reference.md)。本建议优先实现原型，不包含自动开启记录、外部发布或大规模插件框架改造。
